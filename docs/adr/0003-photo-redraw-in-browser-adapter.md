# ADR-0003: 사진은 감정 어댑터 안에서 브라우저로 다시 그려 보내고, 서버는 거절만 한다

- 날짜: 2026-10-23
- 상태: 확정 (2026-10-23 — 사용자 승인)
- 정한 사람: 함께 (10/21 사용자 결정 F·G·H·I를 바탕으로 architect가 제안 — 10/23 사용자 승인)
- Refs: CAREER-26

## 상황
감정을 받으려면 사진이 브라우저 밖(서버 → AI)으로 나가야 한다. 휴대폰 원본은 크고 위치 정보(EXIF GPS)를 담고 있으며, 공개 서비스라 안전 최소한은 '위치 정보 지우기 · 사진 보관 안 함'이다(10/21). 서버 입구(contracts/appraise-http.md)는 CAREER-25에서 JPEG만 · 1,000,000바이트 · 긴 변 1024px · GPS 거절로 확정되었고, 서버는 사진을 고치지 않는다. 남은 결정은 **누가, 어디서, 무엇으로** 사진을 줄이고 지우느냐다. 이 결정이 '기기를 떠나는 것'을 정하므로 공개 뒤에 바꾸면 개인 정보 약속이 바뀐다.

## 결정
사진은 감정 어댑터(`app/src/appraise.js`) 안에서만 처리한다: 브라우저 기본 `createImageBitmap(file, { imageOrientation: 'from-image' })` → `<canvas>`(긴 변 ≤ 1024, 키우지 않음, 흰 바탕) → `toBlob('image/jpeg')`로 **픽셀만 다시 그린 JPEG**를 만들어 그 자리에서 한 번 보낸다. 그래서 EXIF·XMP는 GPS뿐 아니라 통째로 빠지고 방향은 픽셀에 굽힌다. 서버는 줄이거나 지우지 않고, 맞지 않으면(GPS 포함) 거절만 한다.

## 버린 대안
### 대안 1: 서버가 줄이고 EXIF를 지움 (sharp 등)
- 좋은 점: 브라우저마다 다른 동작이 없다. 브라우저를 거치지 않은 요청도 고쳐서 받는다
- 나쁜 점: GPS가 든 원본(수 MB)이 기기를 떠나 서버 메모리를 지난다. 네이티브 이미지 의존성이 믿지 않는 입력을 푸는 공격면이 된다. 업로드가 커진다
- 왜 아님: '위치 정보를 지운 뒤 처리'(CLAUDE.md §9)와 결정 I(서버는 지워 주지 않고 거절)에 어긋난다

### 대안 2: 브라우저에서 EXIF 바이트만 잘라 냄 (piexifjs 등, 다시 굽지 않음)
- 좋은 점: 화질 손실이 없다
- 나쁜 점: 줄이기를 못 한다(결정 F 1024px). Orientation만 남기면 다른 EXIF 처리가 까다롭고, 다 지우면 세로 사진이 눕는다. 의존성이 하나 는다
- 왜 아님: 어차피 줄이려면 다시 그려야 하고, 다시 그리면 지우기가 공짜로 따라온다

### 대안 3: 이미지 압축 라이브러리 (browser-image-compression 등)
- 좋은 점: 품질 맞추기·워커 처리가 들어 있다
- 나쁜 점: 안에서 하는 일은 같은 canvas다. 판(버전)마다 EXIF·방향 처리 기본값이 다를 수 있어 우리가 보장하려는 성질이 남의 기본값에 기댄다
- 왜 아님: 브라우저 기본 기능으로 40줄 남짓이면 된다(CLAUDE.md §8 단계 3)

### 대안 4: 화면(App)이 고를 때 준비하고, 어댑터는 받은 Blob을 보내기만
- 좋은 점: 고르자마자 못 읽는 사진을 알리고, 미리보기도 보낼 사진으로 보일 수 있다
- 나쁜 점: 보내는 파일(어댑터)과 지우는 파일(App)이 달라져, 지우지 않은 사진이 나갈 길을 코드 리뷰로만 막는다. contracts/appraise.md §2 입력 모양이 바뀐다
- 왜 아님: `fetch`가 있는 유일한 파일이 지우기도 해야 '원본이 나가는 길이 없다'(CAREER-26 AC-5(3))가 구조로 지켜진다

## 결과
### 좋아지는 것
- 기기를 떠나는 것은 언제나 1024px 이하, EXIF 없는 JPEG 하나다. 서버·AI·로그 어디에도 원본이 닿지 않는다
- 새 의존성 0. 서버 입구 약속(contracts/appraise-http.md)은 바뀌지 않는다
- 브라우저를 거치지 않은 요청은 서버가 그대로 거절한다 — 두 겹이지만 서로 기대지 않는다

### 나빠지는 것
- 다시 굽기라 화질이 조금 떨어진다(품질 0.85부터)
- 방향·인코더 동작이 브라우저마다 다를 수 있는데, e2e는 Chromium만 본다
- 기기의 CPU·메모리를 쓴다(4000×3000 사진을 한 번 그림)

### 위험과 대비
- 다른 브라우저가 방향을 무시함 → `imageOrientation`을 명시한다. 연결 스토리에서 사용자가 휴대폰(iOS Safari)으로 한 번 확인한다
- 누군가 원본을 그대로 `body`에 넣음 → CAREER-26 AC-5(3)·AC-12 e2e가 빨강이 된다. 서버는 GPS·픽셀로 다시 막는다
- 서버에서 지우기가 필요해지면(예: 앱이 아닌 클라이언트) 이 ADR을 대체하는 새 ADR로 정한다 — 결정 I를 바꾸는 일이라 사용자 결정
