# ADR-0006: 사람별 요청 수 제한은 서버 코드에서, CloudFront가 본 접속 주소 하나로 사람을 가르고, 1분 5번 + 하루 50번을 메모리에서 센다

- 날짜: 2026-10-24
- 상태: 확정 (2026-10-24 — 사용자 승인, CAREER-31 plan D1·D2·D4·D5·D9. 값 1분 5번·하루 50번 · 서버 코드에서 세기 · WAF 버림은 10/24 사용자 결정 U2·U3)
- 정한 사람: 함께 (U2·U3 사용자 결정을 바탕으로 architect가 제안 — 10/24 사용자 승인)
- Refs: CAREER-31

## 상황
하루 상한 300회(CAREER-27, ADR-0004)는 돈을 막지만, 한 사람이 그날 몫을 다 쓰면 나머지 모두가 '퇴근'을 본다. 밖에 열기(CAREER-30) 전에 한 사람이 쓸 수 있는 몫을 줄여야 한다(결정 B). 로그인이 없으므로 '사람'은 접속 주소로 가를 수밖에 없고, 서버(EC2)에는 CloudFront를 거쳐 오므로 소켓 주소는 CloudFront의 주소다. 서버는 한 대·프로세스 하나다(ADR-0004 가정). 사람을 가르는 값과 세는 자리를 공개 뒤에 바꾸면 화면·인프라·로그 읽는 법이 함께 바뀌므로 ADR로 남긴다.

## 결정
`api/`의 새 모듈 `person-limit.js`가 우리 경로·메서드를 지난 **모든 요청**(기억 hit·입력 거절 포함)을 **본문을 읽기 전에** 센다. 사람은 `CloudFront-Viewer-Address` 헤더 **하나**에서 포트를 떼고 IPv4는 주소 그대로, IPv6는 앞 64비트로 가르며, 헤더가 없거나 모양이 틀리면 모두 한 사람(`-`)이다. 셈은 프로세스 메모리의 Map(최대 `PERSON_MAX_ENTRIES`, 오래 안 쓴 것부터 버림)에서 사람마다 최근 1분 미끄러지는 창 5번 + 서울 하루 50번이고, 걸리면 Bedrock을 부르지 않고 429 `person_limit`이다. 걸린 요청은 셈에 넣지 않고, 주소는 로그에 남기지 않는다.

## 버린 대안
### 대안 1: AWS WAF 요청 수 규칙 (spec U3 버린 후보)
- 좋은 점: 요청이 서버에 닿기 전에 막는다. 코드가 없다
- 나쁜 점: 웹 ACL·규칙마다 요청이 없어도 달마다 고정 요금이 붙는다(새 인프라 요금 — spec '새 인프라 요금 없음'과 어긋남). 요청 수 규칙의 창은 몇 분 단위이고 '서울 하루 50번'을 나타낼 수 없다. 기억 hit만 세는지 같은 서버 안 사정을 모른다. 걸렸을 때 본문을 우리 약속(`{"code":…}`)대로 주려면 규칙마다 사용자 지정 응답을 따로 맞춰야 한다. 설정이 다른 저장소(`aws-infra-portfolio`)에 있다
- 왜 아님: 사용자가 10/24 U3에서 서버 코드를 골랐다. 위 이유로 '하루 50번'과 '응답 약속'을 한 곳에서 지킬 수 없다

### 대안 2: 사람별 셈을 파일에 (하루 셈 파일과 같은 식)
- 좋은 점: 서버를 다시 켜도 이어진다
- 나쁜 점: 사람별 셈은 요청마다 바뀐다(하루 셈은 Bedrock 시도마다) — 사람 수만큼 큰 파일을 요청마다 동기로 다시 쓰면 이벤트 루프를 막는다. 파일이 고장 났을 때 '모두 막기'인지 '사람별만 끄기'인지 새 규칙이 필요하다
- 왜 아님: 다시 켜서 비워졌을 때 잃는 것은 '한 사람이 그날 몫을 더 씀'뿐이고 돈은 하루 상한(파일, 이어짐)이 막는다 — 값어치에 비해 비용이 크다(CAREER-31 plan D1)

### 대안 3: `X-Forwarded-For` 또는 소켓 주소로 사람 가르기
- 좋은 점: CloudFront 설정 없이 로컬에서도 값이 있다
- 나쁜 점: `X-Forwarded-For`의 앞부분은 브라우저가 마음대로 넣는다. 소켓 주소는 배포에서 CloudFront 주소라 모두가 한 사람이다. 둘을 섞으면 '어느 값을 믿나'가 요청마다 달라진다
- 왜 아님: spec AC-3 '사람을 가르는 값은 한 가지뿐'

### 대안 4: 고정 1분 창(달력 분) 또는 토큰 버킷
- 좋은 점: 고정 창은 숫자 하나로 된다. 토큰 버킷은 몰림을 부드럽게 받는다
- 나쁜 점: 고정 창은 분 경계 앞뒤로 10번이 된다. 토큰 버킷은 같은 뜻을 소수 셈으로 나타내 테스트와 로그가 읽기 어렵다
- 왜 아님: 미끄러지는 창은 사람마다 시각 5개 배열이라 메모리가 같고, '어느 60초에도 5번 넘지 않음'이 글자 그대로 맞는다

### 대안 5: 걸린 요청도 셈에 넣기
- 좋은 점: 계속 두드리는 사람은 창이 계속 밀려 오래 막힌다
- 나쁜 점: 실수로 여러 번 누른 사람도 같이 묶인다. 문 뒤에 Bedrock이 없어 돈과 상관없다
- 왜 아님: 하루 50번이 이미 상한이고, 더 세게 벌줄 까닭이 지금은 없다

## 결과
### 좋아지는 것
- 한 사람이 하루 300회를 다 쓰지 못한다(한 사람 최대 50요청 — Bedrock 시도로 최대 150)
- 막힌 요청은 본문을 다 읽지 않고(`REJECT_DRAIN_BYTES`까지 버림) Bedrock·하루 셈에 닿지 않는다 — 하루 상한 뒤 홍수(CAREER-27 실패 시나리오 9)도 줄어든다
- 새 인프라·의존성·요금 0. 로그에 주소가 남지 않는다

### 나빠지는 것
- 서버를 다시 켜면 사람별 셈이 모두 비워진다(하루 50번 몫 포함)
- 통신사 주소를 나눠 쓰는 낯선 사람끼리 함께 걸린다(U2에서 받아들임). IPv6는 /64 하나가 한 사람이라 같은 집 안 기기들이 함께 걸린다
- 로컬 dev(헤더 없음)는 모두 한 사람 — 개발자 한 명이 1분 5번에 걸릴 수 있다
- 시험 실행·테스트는 넉넉한 사람별 셈을 따로 넣어야 한다(`createServer`가 꼭 받음)

### 위험과 대비
- **원본(EC2)에 바로 와서 `CloudFront-Viewer-Address`를 꾸밈** → 서버는 그 값을 믿는다. CAREER-30이 원본을 CloudFront에서만 닿게 하고, CloudFront가 브라우저가 보낸 같은 이름 헤더를 덮어쓰는지 확인한다. 그래도 돈은 하루 상한이 막는다
- **CloudFront 원본 요청 정책에 헤더를 안 넣음** → 모두 `-` 한 사람이라 1분 5번에 바로 걸려 드러난다. 로그 `who:"none"`
- **여러 주소를 돌려 쓰는 사람**(주소 6개면 그날 300을 다 씀, Map 상한을 넘기면 셈이 새로 참) → 사람별 제한은 피하지만 돈은 하루 상한이 막는다(spec 남는 위험 (b))
- **서버가 여러 대가 됨** → 사람별 셈이 대마다 따로라 몫이 대 수만큼 커진다. 그때 공유 저장소(ADR-0004 대안 6)로 함께 대체한다
