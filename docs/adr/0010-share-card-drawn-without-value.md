# ADR-0010: 공유 카드는 아저씨 값을 받지 않는 함수가 브라우저 캔버스로 처음부터 그린다

- 날짜: 2026-11-01
- 상태: 확정 (2026-11-01, 사용자 승인)
- 정한 사람: architect 제안 — 사용자 승인 대기 (CAREER-34 plan A1)
- Refs: CAREER-34

## 상황
CAREER-34는 ⑥ 값 공개를 받은 사람이 아저씨 값을 가린 그림을 휴대폰 공유 창으로 보내게 한다. 공개 뒤에는 나간 그림을 되돌릴 수 없으므로 값이 새지 않아야 하고(Jira A-1), 사진이 기기를 떠나는 둘째 길이 생긴다. ADR-0003의 '기기를 떠나는 것은 언제나 1024px 이하, EXIF 없는 JPEG 하나'는 감정으로 보내는 사진의 약속이라 이 길을 다루지 않는다. `appraise`의 모양(contracts §4)과 보내는 길은 바꿀 수 없고, Safari는 버튼을 누른 뒤 오래 걸리면 공유를 거절할 수 있다.

## 결정
카드는 `makeCard(photo, myPrice)` 하나가 그리며 이 함수는 `mochi` · `line`을 받지 않는다. 사진은 `preparePhoto(photo)`로 다시 그린 JPEG만 쓰고, ⑥에 도착할 때 미리 그려 두어 '공유'를 누르면 기다리지 않고 공유 창에 넘긴다. ADR-0003은 그대로이고 감정으로 나가는 길은 바뀌지 않는다.

## 버린 대안
### 대안 1: ⑥ 화면을 찍거나(html2canvas 등) 값을 그린 뒤 덮기
- 좋은 점: ⑥과 카드의 모양이 저절로 같다
- 나쁜 점: 값이 든 DOM이나 픽셀을 거쳐 값이 새는 길이 남는다. 찍는 도구는 새 의존성이다
- 왜 아님: 처음부터 그리지 않아야 어떻게 고쳐도 되살릴 수 없다(CAREER-34 가정 1)

### 대안 2: `appraise`가 준비한 JPEG를 돌려주거나 어댑터가 기억
- 좋은 점: 사진을 다시 그리지 않아 계산이 준다
- 나쁜 점: contracts §4 '다른 키는 없다' · §1 '내보내기 하나'를 깬다. 기억하면 앞 감정의 사진이 남을 수 있다
- 왜 아님: 한 번의 계산을 아끼려고 약속과 상태를 늘린다

### 대안 3: 원본 `File`을 카드에 바로 그림
- 좋은 점: 가장 단순하고 사진이 가장 선명하다
- 나쁜 점: 지우지 않은 입력을 다루는 길이 하나 더 생기고, 큰 사진을 그대로 푼다
- 왜 아님: Jira 전제 '카드에 넣는 사진은 `preparePhoto` 결과'에 어긋난다

### 대안 4: 서버에서 카드를 만듦 (링크별 OG 이미지 등)
- 좋은 점: 눌리는 링크를 줄 수 있고 브라우저 차이가 없다
- 나쁜 점: 사진 보관 · 새 입구 · 요금이 생긴다
- 왜 아님: spec '안 할 것'이고 '사진 보관 안 함'(CLAUDE.md §11)과 부딪친다

## 결과
### 좋아지는 것
- 값이 카드 코드에 들어올 길이 없고, AC-3의 바이트 비교로 글자를 읽지 않고도 확인한다
- 새 의존성 · 서버 요청 · 새 저장이 없다. 눌렀을 때 그리지 않으므로 Safari가 공유를 거절할 까닭이 줄어든다
- 카드는 ⑥에서만 존재해 앞 감정이 남지 않는다

### 나빠지는 것
- 사진을 감정 때 한 번, 카드 때 한 번 다시 그린다(iPhone 계산 · 메모리)
- ⑥ 모양을 고쳐도 카드는 따라오지 않아 두 벌을 맞춰야 한다
- 일단 사용자가 보낸 카드(사진 포함)는 카톡 등에서 지울 수 없다

### 위험과 대비
- **누군가 값을 카드 인자로 더함** → AC-3이 빨강이 되고 PR에서 고의로 확인한다(AC-10)
- **원본 `File`을 그림** → reviewer가 `shareCard.js`의 `createImageBitmap` 인자를 본다. AC-5가 EXIF를 본다
- **그리기 실패 · 메모리 부족** → 문구만 띄우고 ⑥은 그대로다(AC-7 ②)
- **값 말고 사진 자체가 민감함** → 사용자가 공유 창에서 직접 보낼 때만 나간다. 저절로 나가는 길은 없다
