# ADR-0004: 하루 Bedrock 호출 셈은 서버 컴퓨터의 JSON 파일 하나에, 보내기 전에 동기로 읽고·원자적으로 쓴다

- 날짜: 2026-10-23
- 상태: 확정 (2026-10-23 — 사용자 승인) · **(CAREER-31 고침 — 2026-10-24 사용자 승인)** 결정 첫 문장의 자리(`api/var/usage.json`)는 [ADR-0005](0005-usage-file-outside-code-folder.md)로 대체됨. 모양·쓰는 법·막는 쪽 실패는 이 ADR 그대로
- 정한 사람: 함께 (10/23 사용자 결정 U1·U3·U4·U10을 바탕으로 architect가 제안)
- Refs: CAREER-27

## 상황
하루 비용 상한(CAREER-27)은 '그날 Bedrock에 보낸 시도 수'(재시도 포함, U1)를 서울 00:00 기준(U3)으로 세어 `DAILY_CALL_LIMIT`(300, U2)을 넘지 않게 한다. 셈을 메모리에만 두면 서버를 다시 켤 때마다 상한이 새로 생기고, 어떤 요청이 서버를 죽이고 자동 재시작이 되풀이되면 상한이 사라진다 — 그래서 사용자는 '서버 컴퓨터의 파일 하나로 이어간다'(U4)와 '셈을 못 읽으면 부르지 않는다'(U10)를 골랐다. 서버는 프로세스 하나(spec 가정 2)이고 새 인프라(DB)는 이번 범위 밖이다. 남은 결정은 파일의 자리·모양과, 동시 요청·중간에 죽음에도 상한을 넘지 않게 쓰는 법이다. 공개 뒤에 바꾸면 그날 셈을 옮기는 일이 생기고, 틀리면 비용 상한이 조용히 깨지므로 ADR로 남긴다.

## 결정
셈은 `api/var/usage.json`(config `USAGE_FILE`, `api/.gitignore`에 `var/`) 한 파일에 `{"day":"YYYY-MM-DD","used":N}` 모양으로 둔다. Bedrock `send` 바로 앞마다 `take()`가 **사이에 `await` 없이 동기로** 파일을 읽고 → `used < limit`인지 보고 → `used + 1`을 임시 파일에 `flush`(fsync)로 쓴 뒤 이름을 바꿔(rename) 덮고 나서야 보낸다. 파일이 없으면 0, 날짜가 지났으면 0에서 다시, 못 읽거나·모양이 다르거나·못 쓰면 보내지 않고 `unavailable`이다.

## 버린 대안
### 대안 1: 메모리에만 셈 (spec U4 '아쉽게 버린 후보')
- 좋은 점: 가장 작다. 디스크 고장이라는 실패가 없다
- 나쁜 점: 다시 켤 때마다 상한이 새로 생긴다. 죽고-재시작이 되풀이되면 끝이 없다
- 왜 아님: 사용자가 U4에서 '잇는다'를 골랐다

### 대안 2: 덧붙이기만 하는 기록 파일 (시도마다 한 줄, 켤 때 오늘 줄 수를 셈)
- 좋은 점: 고치지 않고 덧붙이기만 해 따져 보기 쉽다(reference 메모 §2의 권고). 쓰기가 덮어쓰기보다 단순하다
- 나쁜 점: 파일이 끝없이 자란다(하루 최대 300줄). 마지막 줄이 반쯤 쓰였을 때 읽는 규칙이 따로 필요하다. 켤 때 읽은 뒤에는 메모리 셈과 파일이 둘이 된다
- 왜 아님: 따져 보기용 덧붙이기 기록은 이미 요청마다의 로그 1줄(`attempts` · `day` · `dayUsed`)이 맡는다. 셈 파일은 '지금 몇 번'만 정확하면 된다

### 대안 3: 날짜별 파일 (`usage-2026-11-08`)
- 좋은 점: 날짜가 바뀌면 저절로 새 파일 — 비우는 규칙이 없다
- 나쁜 점: 파일이 날마다 하나씩 쌓이고 지우는 일이 생긴다. 사용자 결정(U4)의 '파일 하나'와 다르다
- 왜 아님: 한 파일에 날짜를 담아도 '날짜가 다르면 0' 한 줄이면 된다

### 대안 4: 메모리에 셈을 들고, 파일에는 비동기로 뒤따라 씀
- 좋은 점: 이벤트 루프를 막지 않는다. 읽기가 줄어든다
- 나쁜 점: 쓰기가 끝나기 전에 보내면 죽었을 때 셈을 잃는다. 쓰기가 여러 개 겹치면 늦게 끝난 옛 값이 새 값을 덮는다(차례를 맞추는 줄이 필요). 같은 파일을 쓰는 다른 프로세스(시험 실행)의 셈을 못 본다
- 왜 아님: 쓰기는 하루 최대 300번, 한 번에 ≈ 1ms라 막는 비용이 거의 없다. 동기로 하면 잠금·줄 세우기 없이 동시 요청이 섞이지 않는다

### 대안 5: 다른 자리 — 홈 폴더(`~/.how-much/`) 또는 환경변수로 받는 경로
- 좋은 점: 홈 폴더는 worktree를 지워도·코드 폴더를 바꿔 배포해도 남는다. 환경변수는 배포마다 자리를 고를 수 있다
- 나쁜 점: 홈 폴더는 눈에 안 보이는 컴퓨터 전역 상태이고 여러 worktree가 한 셈을 나눠 쓴다. 환경변수는 값을 잘못 주면 조용히 새 파일(0)에서 시작해 상한이 새로 생긴다 — '설정 한 곳'(AC-5)도 둘이 된다
- 왜 아님: 지금은 로컬뿐이다. 자리를 바꾸는 일은 한 번 셈이 0이 되는 것뿐이라 되돌리기 쉽고, 배포 모양이 정해질 때(배포 스토리) 고르는 편이 맞다

### 대안 6: DynamoDB 등 DB의 원자적 더하기
- 좋은 점: 서버 여러 대가 한 셈을 나눠 쓴다. 조건부 쓰기로 '상한 안에서만 +1'이 한 번에 된다
- 나쁜 점: 새 인프라·IAM·요금, 요청마다 네트워크 왕복, DB 실패도 막는 쪽으로 다뤄야 한다
- 왜 아님: spec '안 할 것'(새 인프라 리소스). 서버가 여러 대가 될 때 이 ADR을 대체한다

## 결과
### 좋아지는 것
- 다시 켜도, 보낸 직후 죽어도 그날 셈이 남는다(보내기 전에 다 씀)
- 동시 요청이 몰려도 상한을 넘지 않는다 — 잠금 없이, Node 한 스레드의 동기 구간으로
- 반쯤 쓴 파일을 읽는 일이 없다(임시 파일 + 이름 바꾸기). 고장은 `unavailable` + 로그 `reason`(`usage_store_*`)으로 바로 보인다
- 새 의존성 0, 새 인프라 0

### 나빠지는 것
- `api/src`가 처음으로 디스크에 쓴다(`daily-limit.js` 한 파일, 숫자와 날짜만 — 사진·요청 내용은 들어가지 않음). CAREER-26의 '`api/src`에 파일 쓰기 0' 정적 확인이 이 한 파일 예외로 바뀐다
- 시도마다 파일 읽기·쓰기(동기)가 이벤트 루프를 잠깐 막는다(쓰기 하루 최대 `DAILY_CALL_LIMIT`번)
- worktree마다 셈이 따로다(로컬에서 서버 둘을 띄우면 상한도 둘)
- 디스크가 고장 나면 상한에 안 걸렸어도 감정이 멈춘다(U10 — 일부러 막는 쪽)

### 위험과 대비
- **배포 때 코드 폴더를 바꿔 넣으면 `api/var/`가 새로 생겨 그날 셈이 0이 된다** → 배포 스토리에서 셈 파일 자리(코드 밖 고정 폴더 등)를 정하고 이 ADR을 고치거나 대체한다. 배포 스토리 완료 조건에 넣을 것을 사용자에게 제안한다(spec U7과 같은 자리) → (CAREER-31 고침 — 2026-10-24 사용자 승인) [ADR-0005](0005-usage-file-outside-code-folder.md)에서 코드 밖 홈 아래 자리로 정함
- 누가 파일을 지우면 그날 셈이 0 → 서버 컴퓨터 접근이 필요한 일이라 받아들인다. 로그 `dayUsed`가 갑자기 작아지면 보인다
- 전원이 나가 폴더 기록이 이름 바꾸기 전으로 돌아가면 몇 건 덜 센다 → 받아들임(폴더 fsync는 넣지 않음)
- 같은 파일을 두 프로세스가 쓰면 드물게 1건 놓친다 → 서버는 하나(가정 2). 서버가 여러 대가 되면 대안 6으로 대체
- 시계가 자정을 넘어 뒤로 가면 → 파일 날짜가 더 늦으면 그 셈을 그대로 써서 상한이 새로 생기지 않는다
